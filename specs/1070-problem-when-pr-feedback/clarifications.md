# Clarifications: Distinguish PR-feedback fixer timeout from stuck-loop, and let it self-recover

**Issue**: [generacy#1070](https://github.com/generacy-ai/generacy/issues/1070)
**Branch**: `1070-problem-when-pr-feedback`

## Batch 1 — 2026-07-28

### Q1: Same-SHA persistence mechanism
**Context**: FR-006/FR-007 gate the "one retry" budget on "same branch head SHA". Spec §Assumptions #6 explicitly forbids new Redis key patterns and new files under `/var/lib/generacy/`, and existing `MonitorState` (see `packages/orchestrator/src/types/monitor.ts:197`) has no per-issue slot. Today the monitor only carries per-`stateKey` in-memory maps like `lastUnresolvedThreadCount: Map<string, number>` at `pr-feedback-monitor-service.ts:79`. This choice decides whether the retry budget survives a worker restart mid-timeout.
**Question**: Where should the "SHA at last timeout" be recorded?
**Options**:
- A: In-memory `Map<stateKey, sha>` on `PrFeedbackMonitorService` (mirrors `lastUnresolvedThreadCount`; simplest; forgets on worker restart → a restart between the two timeouts silently re-enables the retry budget)
- B: A marker comment on the PR body or a dedicated PR-level comment (`<!-- generacy-cockpit:fixer-timeout-sha:<sha> -->`), read via `listPrCommentBodies` (durable across restart; matches the #1047 acknowledgment-marker pattern; one extra GitHub read per poll)
- C: A field parsed off `blocked:fixer-timeout` itself — encode the SHA in the label name (e.g., `blocked:fixer-timeout-<short-sha>`) so the label carries its own state (durable, zero storage; label name churn; harder for humans to remove correctly)
- D: Reopen SC-006 and add a Redis key under `orchestrator:pr-feedback:timeout-sha:<owner>/<repo>#<pr>` (durable; violates the current SC-006 wording — would require rewording that success criterion)

**Answer**: **A** — in-memory `Map` on `PrFeedbackMonitorService`. Mirrors the sibling `lastUnresolvedThreadCount` map and adds zero GitHub API calls (load-bearing: cluster + operator share one 5k/hr limit; a new per-poll GraphQL read is exactly the shape that produced recent `/cockpit:auto` rate-limit exhaustion). Restart-loss failure mode is bounded and benign — an orchestrator restart grants at most the Q5 cap again (one or two extra 20-min cycles, only if threads still unresolved), which is strictly better than today's permanent wedge. Combined with Q5=C, the value stored is a **small integer counter per trigger**, NOT a SHA — see Q5 for the corrected framing. Reject C (unbounded label proliferation in shared repo namespace); D is cleanest in isolation but SC-006 forbids it. If A proves too lossy in practice, escalate to B (gated on `blocked:fixer-timeout*` being present so the normal path stays free).

### Q2: Timeout signal path from CLI runner to disposition logic
**Context**: FR-001 requires the branch condition to be `!success && timedOut` at minimum, but `spawnClaudeForFeedback` at `pr-feedback-handler.ts:412` returns a single `boolean success`; the `timedOut` variable set at `:759` is a local inside `runCli` and returns as `false` at `:791` with no way for the caller (`handleAddressPrFeedback`) to distinguish timeout from a clean non-zero exit. This decides the shape of the private API change.
**Question**: How should `timedOut` reach the disposition logic in `handleAddressPrFeedback`?
**Options**:
- A: Change `spawnClaudeForFeedback` return type from `Promise<boolean>` to `Promise<{ success: boolean; timedOut: boolean }>` (explicit; forces every caller to acknowledge the new dimension; touches the test doubles at `pr-feedback-handler.test.ts`)
- B: Widen to `Promise<{ success: boolean; exitCode: number | null; timedOut: boolean }>` — expose `exitCode` too, since the spec itself uses `exitCode: 143` as the timeout signature (matches the log payload shape at `:788`; slight overreach if downstream never uses `exitCode`)
- C: Keep the boolean return and expose `timedOut` as a mutable field on the handler instance (`this.lastCliTimedOut`), read immediately after the `await` (avoids type change; introduces hidden state; harder to test)
- D: Emit an event / callback (`onCliOutcome`) rather than a return-value change (over-engineered for a two-caller path)

**Answer**: **B** — widen `spawnClaudeForFeedback` return type to `Promise<{ success: boolean; exitCode: number | null; timedOut: boolean }>`. The defect was *diagnosed* by spotting `exitCode: 143` in the worker log; the fix should make that signal first-class rather than something a future reader re-derives. `exitCode` is already in the log payload at `:788`, so disposition logs can state it authoritatively instead of inferring timeout from a boolean. YAGNI objection is fair but cheap to overrule — widening a two-caller private return type once costs less than widening it twice. Reject C outright: a mutable `this.lastCliTimedOut` read after an `await` is hidden temporal coupling with no enforcement that nothing else touches the field between write and read; the option's own text concedes it is harder to test.

### Q3: Disposition when the CLI times out AND `hasChanges === false`
**Context**: FR-001 names three sub-branches — `timeout`, `no-diff`, `push-failed` — but the combination "CLI timed out AND no partial push landed" is not clearly mapped. FR-006's retry pre-condition is "the previous cycle pushed at least one commit", so a zero-commit timeout is NOT retry-eligible. US2's AC only covers retry when a commit was pushed. Spec §Assumptions #4 asserts retry budget resets on new SHA — but if no push ever happened, there is no new SHA to key off. The observed field failure in #1070 always involved a partial push, but the code must handle both.
**Question**: What label should apply when `timedOut === true && hasChanges === false` (fixer ran out of time before writing any commit)?
**Options**:
- A: `blocked:stuck-feedback-loop` (treat zero-commit-timeout as "made no progress", same as no-diff; simplest; loses the "was a timeout" signal for operator triage)
- B: `blocked:fixer-timeout` with a payload flag indicating `hasChanges: false`, and the monitor's retry gate at FR-006 refuses to re-dispatch because the pre-condition fails (retry label is applied but explicitly non-retriable; operator must remove manually; matches "timeout is the true story")
- C: A new terminal label `blocked:fixer-timeout-no-progress` distinct from `blocked:fixer-timeout-repeat` (three timeout-family labels total; most precise; more label vocabulary to maintain)

**Answer**: **C** — introduce distinct terminal label `blocked:fixer-timeout-no-progress`. Reject A: it reintroduces this issue's exact bug — the whole #1070 complaint is that the label named the wrong cause and sent an operator hunting for a loop that did not exist; choosing `blocked:stuck-feedback-loop` for a zero-commit timeout does precisely that again, just for a narrower case. Reject B: if `blocked:fixer-timeout` sometimes has a retry coming and sometimes silently does not, the operator cannot tell which from the label — a label whose meaning depends on invisible state is the problem, not the fix. **Fallback if three timeout-family labels is judged too much vocabulary**: reuse `blocked:fixer-timeout-repeat` for this state (both mean "timed out, no auto-retry, a human is needed"). Option A is not an acceptable simplification.

### Q4: `waiting-for:address-pr-feedback` handling on timeout disposition
**Context**: Today's Disposition B (`pr-feedback-handler.ts:469-481`) explicitly keeps `waiting-for:*` in place so the operator sees the pause. On the new `blocked:fixer-timeout` branch, the monitor at FR-006 will re-enqueue automatically and re-add `waiting-for:*` inside `pollRepo` at `pr-feedback-monitor-service.ts:402`. This determines whether the label is briefly absent between the timeout and the retry-tick, and whether an operator watching the issue sees `blocked:fixer-timeout` alone or `blocked:fixer-timeout + waiting-for:address-pr-feedback` together.
**Question**: On the new `blocked:fixer-timeout` branch, should `waiting-for:address-pr-feedback` be cleared or kept?
**Options**:
- A: Keep it (matches Disposition B; operator sees "still waiting"; the auto-retry's re-add is a no-op; label state is stable across the retry boundary)
- B: Clear it and let the monitor re-add on the retry tick (matches the "fresh cycle" framing of FR-008; label churn is visible; briefly the issue shows `blocked:fixer-timeout` alone)
- C: Clear it and DO NOT re-add on retry — treat the retry as a continuation of the same "waiting" state (least churn; requires monitor to skip the re-add on retry-branch dispatch; more code)

**Answer**: **A** — keep `waiting-for:address-pr-feedback` in place. Decisive reason: **any window in which `waiting-for:*` / `agent:*` is absent is a window in which an incoming review is silently dropped.** We hit exactly that failure this session — PR reviews were discarded on a PR whose issue lacked an `agent:*` label, with no error anywhere. B deliberately opens such a gap between the timeout and the retry tick and buys nothing for it; the "fresh cycle" framing is cosmetic. A also matches today's Disposition B, keeps label state stable across the retry boundary, and makes the monitor's re-add a harmless no-op. C requires the monitor to special-case the retry dispatch — more code for less clarity.

### Q5: Retry-budget behavior when the retry itself pushes a new commit but also times out
**Context**: Spec §Assumptions #4 states the retry-once budget "resets naturally at each new SHA". Consider: cycle 1 pushes commit A (partial), times out → `blocked:fixer-timeout`. Monitor auto-retries. Cycle 2 pushes commit B on top of A (further partial), times out again. The branch head SHA has advanced from A → B. Under a strict reading of Assumption #4, the budget resets → cycle 3 auto-retries too → this can chain indefinitely as long as each retry makes any commit at all. This is the "chained-partial-progress infinite loop" edge case. FR-007 as written checks "same head SHA" — under this reading, cycle 2 does NOT apply `blocked:fixer-timeout-repeat` because the SHA changed.
**Question**: Should the retry budget reset when a retry pushes a new commit but also times out?
**Options**:
- A: Yes, budget resets — matches Assumption #4 literally. Chain continues as long as each cycle makes ANY progress. The failsafe is that eventually the fixer will run out of things to do and either succeed (Disposition A) or produce a no-diff cycle (Disposition B → `blocked:stuck-feedback-loop`, no auto-retry).
- B: No, apply `blocked:fixer-timeout-repeat` on any second consecutive timeout regardless of whether the SHA advanced — retry-once means retry-once per PR-feedback trigger, not per SHA. Simplest budget, no chain-progress edge case; potentially cuts off legitimate long reviews after two 20-min windows.
- C: Track a small integer counter (e.g., max 2 total auto-retries per trigger, resetting only when the review threads are fully resolved) — bounded chain support; requires a counter, not just a SHA.

**Answer**: **C** — bounded counter, max 2 auto-retries per trigger, reset only on full thread resolution. **A's failsafe does not hold** and this is the load-bearing correction: A argues the chain terminates because the fixer eventually produces a no-diff cycle, but a fixer that times out **never reaches the no-diff branch** — it exits through the timeout branch every single cycle. So the terminating condition A relies on is unreachable for exactly the population A applies to. Any cycle that writes one trivial commit advances the SHA and refills the budget → genuine unbounded loop, 20 minutes per iteration, consuming a worker the whole time. B is defensible and simple but cuts off a legitimately large review after two windows even when each cycle was making real headway. C keeps the bound while staying progress-aware: resetting on "threads fully resolved" (i.e., the work actually completed) is the right condition; resetting on "any commit" is what makes A unbounded; resetting on "done" cannot. **Implementation note (rewrites Q1)**: the counter keys on the same identity the budget is scoped to (per PR-feedback trigger, i.e., `stateKey`) — so Q1's in-memory `Map` holds a **small integer counter**, not a SHA. FR-006/FR-007/Assumption 4's "same head SHA" framing predates this answer and must be replaced with counter-based wording in spec.md.
