# Clarifications for #1053

*Feature*: Gate IDs must not collide across runs — a terminal gate blocks reopening the same (issueRef, gateType, generation)
*Branch*: `1053-problem-gateid-pure-function`

## Batch 1 — 2026-07-27

### Q1: Concrete identity source for the per-run discriminator
**Context**: The spec's `[NEEDS CLARIFICATION §1]` and FR-001 both require adding a per-run discriminator to `gateKey`, but leave the identity source open. The choice determines (a) whether the discriminator flows explicitly through the tool input or is derived from ambient MCP-server state, (b) how takeover under #1015 composes (a takeover MUST mint a fresh discriminator — otherwise US1's takeover trigger path silently regresses), (c) whether an MCP-server restart mid-run breaks within-run idempotency (US2), and (d) which package owns the identity mint.
**Question**: Which identity source should the per-run discriminator use?
**Options**:
- A: **The auto-run id already minted by `/cockpit:auto` for its ledger** (shape `christrudelpw-snappoll-1-20260727-200458` — cluster+repo+issue+timestamp). Threaded through as an explicit tool input field. Survives MCP-server restarts within a run because the auto-loop skill re-passes it every wake tick. A takeover mints a fresh timestamp → fresh id → US1 takeover path holds by construction. Requires the run id to travel on every `cockpit_gate_open`/`cockpit_gate_ack` invocation.
- B: **The MCP-server `INSTANCE_NONCE`** (`packages/generacy/src/cli/commands/cockpit/mcp/event-bus.ts:72`, 16 hex chars from `crypto.randomBytes(8)`, per-MCP-process, per #1015 planning notes). Derived from ambient state — no wire/tool-input change. But scope is *process lifetime*, not *run lifetime*: an MCP-server restart mid-run would flip the discriminator, breaking within-run idempotency (US2 AC-3 explicitly forbids process-lifetime scope). Suitable only if the MCP server is guaranteed to outlive the run.
- C: **A fresh discriminator minted by the tool itself and persisted for the run duration** (e.g. written to a per-run file the tool re-reads on each call, keyed by `sessionId` or claim marker). No caller changes; survives restarts because it's on disk. Introduces a new persistence surface the tool must own and reason about lifecycle for.
- D: **The `sessionId` already passed by the plugin to `cockpit_gate_open`** (`GateOpenInputSchema.sessionId` at `schemas.ts:102`). Zero new fields. But `sessionId` today identifies the *conversation/session*, not the *auto run*; conflating them changes its semantics and couples this fix to whatever the plugin passes there, which under #1015 is likely to be the claim's `INSTANCE_NONCE` (same trap as B).

**Answer**: **A** — the auto-run id, threaded as an explicit tool input. B and D fail for the same reason: process/session lifetime is not run lifetime. US2 AC-3 explicitly forbids process-lifetime scope, and D additionally conflates `sessionId`'s meaning (under #1015 it is likely to *become* `INSTANCE_NONCE` — the same trap one level of indirection away). C introduces a new on-disk persistence surface — the stale-key/TTL class of bug (#849) that sibling #1051 deliberately avoided under its FR-007 ("no new persisted state"). A survives MCP-server restarts because the auto-loop re-passes the id on every wake tick, and a takeover mints a fresh timestamp, so the US1 takeover path holds by construction. **Required addition:** document the behaviour when no `runId` is supplied — `cockpit_gate_open` is callable outside `/cockpit:auto`. Without an explicit fallback those callers silently keep today's colliding behaviour and the bug survives for exactly the manual path an operator would use to work around it. Mint a per-process fallback and log at `info` which source was used.

### Q2: Detection mechanism for the terminal-collision cloud drop
**Context**: The spec's `[NEEDS CLARIFICATION §2]` and FR-004 require the cluster to surface the cloud's `[relay] Ignoring gate-open for terminal gate` drop as an error at the `cockpit_gate_open` call site. Today the cloud returns `202 Accepted` and drops the frame downstream on the relay side, so the current tool at `cockpit_gate_open.ts:107-114` legitimately reports success. Choosing the mechanism decides whether this issue blocks on the companion generacy-cloud PR, how long the tool call takes on the happy path, and whether the cluster needs a new relay-channel subscription.
**Question**: How should the cluster detect that the cloud dropped a `gate-open`/`gate-outcome` frame as terminal-collision?
**Options**:
- A: **Block on the companion generacy-cloud API change** to signal terminal-collision synchronously (cloud returns non-`202` with a distinguishable code when the doc is already terminal). Preferred by the spec. Sequences this issue behind the cloud PR landing. Zero cluster-side polling; single request/response. Requires cross-repo coordination and adds this issue to the cloud PR's blast radius.
- B: **Cluster-side probe via `cockpit_gate_list` / `cockpit_gate_status` after POST** — after `202 Accepted`, poll the cloud for the gate's status until it resolves to `open` (success) or `applied`/`superseded`/`failed` (collision → error) or a timeout fires (network error). No cloud API change needed → unblocks this issue immediately. Adds latency to every `gate-open` call (must wait for the poll to confirm) and load on the list/status endpoints. Requires picking a poll cadence + timeout budget.
- C: **Consume a `cluster.cockpit` relay-channel event carrying the drop signal** (companion cloud change: instead of a synchronous API change, cloud publishes a `gate-open-dropped` event on the relay). Cluster subscribes and correlates by `gateId` back to the in-flight tool call. Adds an async correlation surface (in-flight table keyed by `gateId`, timeout, cleanup) — meaningfully more complex than A or B. Best fit for the existing retain-and-replay model landed by #1024.
- D: **Hybrid — B as the shipped mechanism, migrate to A once the companion lands.** Ships this issue independently on option B; when the cloud PR lands, swap the detection path to A and drop the polling. Doubles the implementation cost (both mechanisms land) but decouples the two release trains.

**Answer**: **A — but decoupled, not blocking.** Companion is **generacy-ai/generacy-cloud#887**, already filed and queued. The framing that matters: once Q1 lands, terminal collisions stop occurring. FR-004 detection is a backstop for a case the primary fix eliminates — so it must not gate the primary fix on a cross-repo dependency. Ship the Q1 discriminator now, independently. Land FR-004 detection as a follow-up once #887's rejection reply exists. Rejecting B: it puts a poll on the happy path of every `gate-open`, permanently, to detect something that should become vanishingly rare. Rejecting D: it ships two mechanisms and pays for both.

### Q3: Wire representation of the run discriminator
**Context**: FR-002 requires the wire contract stay compatible with the cloud's `gateOpenPayloadSchema` and the mirrors in `docs/cockpit-remote-gates-plan.md` + `generacy-cloud/specs/843-part-cockpit-remote-gates/contracts/gates-wire.md`. FR-010 explicitly leaves open "any additive field the run discriminator demands, *if* the plan chooses to expose it as a first-class wire field rather than fold it into `gateKey` composition." The choice determines whether the cloud parser needs any change at all, whether the discriminator is observable on the wire for cloud-side filtering/analytics, and how forward/backward compat during rollout works.
**Question**: How should the run discriminator appear on the wire?
**Options**:
- A: **Fold into the `gateKey` pre-image string only** — new shape `${issueRef}:${gateType}:${generation}:${runId}`. `gateId = sha256(gateKey).slice(0, 24)` unchanged. No `GateOpenWireSchema` field change, no cloud schema change: the cloud sees a longer string it hashes as opaque bytes, produces a different `gateId`, treats the frame as a fresh gate by construction. Discriminator is NOT independently queryable on cloud docs (it's baked into `gateKey` which is also stored). Zero cross-repo schema coordination.
- B: **Add an explicit `runId` field to `GateOpenWireSchema` + cloud `gateOpenPayloadSchema`** — discriminator travels as its own field, and `deriveGateKey` reads it. Cloud can query/filter/index by `runId` (useful for cloud-side observability — "show me all gates from run X"). Requires coordinated cloud schema update; FR-002 mirror update mandatory. Additive-only per FR-010; existing field shapes untouched.
- C: **Both — fold into `gateKey` AND surface as an additive wire field.** `gateKey` is what determines identity; the exposed `runId` field is a redundant read-only projection for observability. Belt-and-suspenders. Costs one more Zod field, buys cloud-side queryability.
- D: **Neither on the wire — recompute the discriminator cloud-side from something already on the frame** (e.g. hash `sessionId` + `serverTime`). Keeps the wire narrow but couples cloud identity derivation to cluster-side ambient state the cloud can't verify. Fragile; rejected as a straw-man unless there's a compelling reason.

**Answer**: **A — fold into the `gateKey` pre-image only.** Decisive: A requires no cloud schema change at all, which is precisely what makes Q2's decoupling achievable. The cloud hashes a longer opaque string, derives a different `gateId`, and treats the frame as a fresh gate by construction. **Correction to the option text:** it says the discriminator is "NOT independently queryable". It is not *indexed*, but it is *recoverable* — `gateKey` is stored on the doc, so `christrudelpw/snappoll#1:phase-queue:P2:<runId>` is right there for debugging. That is sufficient; add B's explicit field later only if cloud-side analytics actually need an index.

### Q4: `askedAt` handling to preserve within-run idempotency
**Context**: FR-003 explicitly flags this as a choice that "must be explicit." The current within-run non-determinism is `askedAt: new Date().toISOString()` computed inside `cockpit_gate_open` at `cockpit_gate_open.ts:72`. Two retried calls for the same natural gate produce byte-different `gateOpenWire` records that differ only in `askedAt`. US2 requires the second call be a no-op that the operator observes as exactly one inbox row. The chosen approach determines whether cloud dedup is load-bearing for correctness or just for optimization.
**Question**: How should `askedAt` be handled to preserve within-run `cockpit_gate_open` idempotency?
**Options**:
- A: **Hoist `askedAt` above the retry boundary** — compute once per natural gate (e.g. cache keyed by `gateId`), reuse on every retry. Retried frames are byte-identical. Correctness of US2 does not depend on cloud dedup at all — even a broken cloud dedup would still show exactly one inbox row because the two frames are literally the same bytes. Adds a small cache in the tool.
- B: **Accept per-call `askedAt`; rely on cloud `gateId`-keyed dedup** for US2. Frames differ in `askedAt` but hash to the same `gateId`, so the cloud writes only one doc. Simpler cluster code (no cache); makes US2's correctness depend on the cloud correctly deduping by `gateId` on write. Under FR-004's terminal-collision path the same dedup mechanism is the *bug source*, so this option ties two orthogonal cloud behaviours together — dedup for open gates (must work) vs dedup for terminal gates (must NOT work with the new discriminator).
- C: **Both — hoist `askedAt` AND rely on cloud dedup.** Redundant safety. Cheap; keeps US2 correct even if the cache is buggy or the cloud dedup regresses.
- D: **Drop `askedAt` from `GateOpenWireSchema` entirely** — cloud stamps its own `receivedAt` on write; cluster's ask-time isn't load-bearing. Removes the non-determinism at the source. Loses the cluster-side timing signal the field currently carries (useful for latency debugging). Breaks FR-010's "zero removed or renamed fields" invariant.

**Answer**: **A — hoist `askedAt` above the retry boundary.** Option B's own description contains the disqualifying argument: it makes US2's correctness depend on the cloud's `gateId` dedup, which under FR-004 is *the bug source*. Correctness must not rest on the mechanism being worked around. With A, two retried frames are byte-identical, so exactly one inbox row appears even if cloud dedup were entirely broken. Cloud dedup remains a backstop we do not rely on — which is C in substance, but the stated intent matters: **do not treat cloud dedup as load-bearing.**

### Q5: Error return shape for terminal-collision (FR-005)
**Context**: FR-005 requires the terminal-collision error be *distinguishable* from generic transport / invalid-args / internal errors so the auto loop (FR-006) can branch on it. The spec explicitly leaves the shape open — "e.g. a new `ToolResult` error class `'terminal-collision'` distinct from `'transport'` / `'invalid-args'` / `'internal'`, or a stable error code inside `detail`." The choice affects the caller's branching code, the ToolResult type surface, and how many other in-flight PRs (#1015, #1020, #1024) will inherit the new class value.
**Question**: How should terminal-collision be represented in the tool's error return?
**Options**:
- A: **New top-level `ErrorClass` value `'terminal-collision'`** on the existing `ToolResult` discriminator (same shape used by `'claim-conflict'` in #1015 planning notes). Callers branch on `class` — one strong static enum, exhaustive-switch-friendly. Bumps the class union; every consumer that switches on class needs a new branch (compiler catches it).
- B: **Keep the existing `'transport'` (or similar) class, but add a stable string code inside `detail.code`** (e.g. `detail.code === 'CLOUD_TERMINAL_COLLISION'`). Zero change to the class union → no consumer-side compile break, but the branching is stringly-typed on `detail.code` — easy to typo, no exhaustiveness. Matches the code-inside-detail pattern used elsewhere in the CLI.
- C: **Both — new class value AND stable code inside `detail`.** Class for structural branching, code for logging/telemetry keying. Redundant but zero-cost if a class value is being added anyway.
- D: **Reuse an existing class (`'internal'` or `'transport'`)** and rely on the auto loop to grep the human message. Rejected as a straw-man — grep-on-message is a documented anti-pattern in the cockpit MCP-tool contract set (#807 / #822 introduced `resolveIssueContext` specifically to escape a similar `/bare issue number/.test(message)` sentinel).

**Answer**: **A — new `ErrorClass` value `'terminal-collision'`.** Matches the `'claim-conflict'` precedent, gives exhaustive-switch safety, and D is a documented anti-pattern (#807 / #822 exist specifically to escape message-grepping). **Real cost flagged:** adding a class value will break exhaustive switches in #1015, #1020 and #1024. That is the compiler doing its job rather than a reason to choose B — but expect merge friction and coordinate the landing order.
