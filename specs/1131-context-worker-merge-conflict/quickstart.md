# Quickstart: Merge-conflict re-arm targets a resolution-scoped review

**Feature**: `1131-context-worker-merge-conflict`
**Status**: Complete

Orientation for the implementer. This feature has no user-facing CLI surface —
it changes how the orchestrator worker re-arms after an autonomous merge-conflict
resolution.

---

## What changes, in one paragraph

After `MergeConflictHandler` cleanly resolves a merge conflict, it re-arms into a
**`review` phase scoped to the resolution diff** (`HEAD^1..HEAD` — the pre-merge
branch tip vs. the `--no-ff` merge commit) instead of re-running the interrupted
phase. A clean scoped review flows forward to `validate`; a review with findings
enters `remediate`. Gated by `reviewPhaseEnabled`; with the flag off, behavior is
byte-identical to today.

---

## Feature flag

```bash
# Enables the scoped-review re-arm (and the review phase generally)
export WORKER_REVIEW_PHASE_ENABLED=true
```

`reviewPhaseEnabled` lives on `WorkerConfigSchema` (default `false`). With the
flag off, the handler re-arms `startPhase: metadata.phase` and resolves via
labels exactly as before.

## Implementation order (matches plan.md § Approach)

1. **Types** — `ReviewScope`; add `reviewScope?` to `ReArmedOutcome`
   (`handler-outcome.ts`) and `WorkerContext` (`worker/types.ts`); widen
   `WorkerContext.resumeReason` to include `'merge-conflict-resolved'`.
2. **Handler** — in `finishSuccess` (`merge-conflict-handler.ts:659`), branch on
   `config.reviewPhaseEnabled`:
   - ON → compute `reviewScope` (`{ baseSha: HEAD^1, headSha: HEAD }`; `{HEAD,
     HEAD}` on the no-op path; `undefined` when SHAs can't be resolved) and
     return `{ outcome: 're-armed', startPhase: 'review', reviewScope }`.
   - OFF → return `{ startPhase: metadata.phase }` (unchanged).
   - Keep the `metadata.phase` fail-loud guard (`:641-656`) intact.
3. **Worker wiring** — carry `startPhase` / `resumeReason` /`reviewScope` into
   `rearmItem.metadata`; in the context-build seam, honor the explicit
   `startPhase: 'review'` override and set `context.reviewScope` on the
   `merge-conflict-resolved` resume path.
4. **Executor + charter** — `review-executor.ts` reads `context.reviewScope`,
   short-circuits an empty window straight to `validate`, and passes the window
   to `buildReviewCharter` as `diffWindow`; `review-charter.ts` names the exact
   `baseSha..headSha` range when `diffWindow` is present.
5. **Tests** — see below.

## Gotchas

- **`metadata.startPhase` does not select the resume phase.** Phase resolution
  is label-based (`PhaseResolver.resolveStartPhase`). The `review` re-arm reaches
  `review` only via the explicit override at the context-build seam — see
  research.md Decision 1. Don't expect the rearm metadata alone to route the run.
- **`undefined` reviewScope ≠ empty window.** `undefined` → whole-branch review
  (FR-010). A *defined but empty* window → short-circuit to `validate`
  (FR-011). Keep these two paths distinct.
- **Flag OFF must stay byte-identical.** The override branch requires
  `startPhase === 'review'`; flag-OFF re-arms `metadata.phase`, so the override
  is never taken and there is no `Unknown starting phase: review` throw.
- **Changeset**: `@generacy-ai/orchestrator` **patch** at
  `.changeset/1131-merge-conflict-review-rearm.md`. Verify no new public export
  slips in (the `diffWindow` charter field and `WorkerContext.reviewScope` are
  package-internal).
