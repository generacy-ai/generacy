# Implementation Plan: Orphaned queue claims must be reclaimed after a worker dies without unwinding

**Feature**: Redis-side reap sweep that reclaims `orchestrator:queue:claimed:<workerId>` hashes whose owning heartbeat key is absent, plus transition-edge `warn` escalation on the four "Dropping ... enqueue (item already in flight)" sites so a wedge is visible in log queries before the reaper fires.
**Branch**: `1054-problem-when-worker-dies`
**Status**: Complete

## Summary

`WorkerDispatcher.reapStaleWorkers` (`packages/orchestrator/src/services/worker-dispatcher.ts:578`) iterates the in-memory `activeWorkers` Map — so a worker that died without unwinding (SIGKILL, container OOM, or the *dispatcher itself* being replaced by a fresh replica) leaves an orphaned claim hash with `ttl = -1` that no reaper cycle can ever see. `orchestrator:queue:in-flight-items` still contains the itemKey; every subsequent `enqueueIfAbsent` returns `false` at `SISMEMBER`; the item is permanently wedged. Observed live: `generacy-ai/generacy#1051` sat blocked for 84 minutes with 17 identical `info`-level drop lines.

The fix per the spec + clarifications:

1. **FR-001 / FR-003 / FR-004 — Redis-side sweep.** A new `RedisQueueAdapter.reapOrphanClaims()` method `SCAN`s `orchestrator:queue:claimed:*` and, for each `<workerId>`, checks `EXISTS orchestrator:worker:<workerId>:heartbeat`. Absent → invoke a new Lua `RECLAIM_ORPHAN_SCRIPT` that (a) re-checks the heartbeat server-side (race-safety per US2), (b) applies the FR-005 grace-window (`now - enqueuedAt < 2 × heartbeatCheckIntervalMs` → abort), (c) atomically `SREM in-flight` + `ZADD pending` (`queueReason: 'resume'`, `attemptCount++`) + `HDEL/DEL claimed`. `WorkerDispatcher.reaperLoop` calls this alongside the existing in-memory `reapStaleWorkers` on the same cadence (`heartbeatCheckIntervalMs`, default 15s). Additive — zero change to `CLAIM_SCRIPT` / `ENQUEUE_IF_ABSENT_SCRIPT` / `release()` / `complete()` / `handleLeaseExpired` (FR-010).

2. **FR-002 / clarifications Q3=C — `attemptCount++` without dead-lettering from the reaper.** The reclaim increments `attemptCount` so a genuinely pathological item (OOM on a giant diff) stays diagnosable via the counter; but the reaper never dead-letters, so a routine cluster restart mid-claim (the observed incident's actual trigger) doesn't steadily condemn healthy work. Dead-lettering stays where it belongs — the `release()` failure path.

3. **FR-006 / FR-007 / clarifications Q4=A — transition-edge `warn` escalation on the drop-log sites.** A new pure-function shared helper `classifyDropSeverity(itemKey, ageMs, thresholdMs, state) → { severity, isTransitionEdge }` is called from the adapter (`redis-queue-adapter.ts:141` + `in-memory-queue-adapter.ts:89`, per FR-011 / Q5=C) and from the four monitor sites (PR-feedback, merge-conflict, clarification-answer, label-resume). Emits `warn` **once** when age crosses the threshold and **once** when it clears — never per-cycle. Threshold is a new `maxRunDurationMs` field on `DispatchConfigSchema` with default `1_800_000` (30 min, per clarifications Q1=A / FR-012). The age is read from the claim hash's `enqueuedAt` field — no schema change (existing on `SerializedQueueItem`).

4. **FR-008 — reclaim event log at `warn`.** Fires once per orphan reclaim with `{ workerId, itemKey, ageMs, attemptCountBefore, attemptCountAfter, reason: 'orphaned-claim-no-heartbeat' }`. Not gated by transition-edge tracking (the reclaim itself is one-shot). Complements the existing in-memory `worker-dispatcher.ts:583-586` warn so log queries can differentiate the two paths.

5. **FR-009 / US4 — regression test.** New `packages/orchestrator/src/services/__tests__/redis-queue-adapter.orphan-reclaim.test.ts` reproduces the exact wedge shape from `generacy-ai/generacy#1051` (claim under synthetic workerId → delete heartbeat → run reap → assert claim gone + itemKey removed from in-flight SET + item re-pending with `queueReason: 'resume'` + `attemptCount = 1` + subsequent `enqueueIfAbsent` succeeds), plus the negative (live heartbeat → survives sweep).

Changeset (`patch`, `workflow:speckit-bugfix`, `@generacy-ai/orchestrator`) is required per the CLAUDE.md-encoded CI gate.

## Architectural Decisions

- **AD-1: Where the reclaim primitive lives — inside `RedisQueueAdapter`, not the dispatcher.** The dispatcher is workflow-aware (it knows about `WorkerHandler`, `LeaseManager`, `labelCleanup`); the adapter is transport-focused (Redis command shape, script atomicity). The reclaim is fundamentally a Redis-side data-integrity operation that happens to be *triggered* by the dispatcher's cadence. Keeping it in the adapter (a) mirrors the existing `CLAIM_SCRIPT` / `RELEASE_SCRIPT` / `ENQUEUE_IF_ABSENT_SCRIPT` pattern, (b) makes the in-memory adapter's no-op version trivial and semantic (in-memory *cannot* have orphans), (c) lets the dispatcher's `reaperLoop` remain a scheduling shell.

- **AD-2: Interface widening on `QueueManager`, not a new interface.** Adding `reapOrphanClaims` to `QueueManager` is chosen over a new `ReclaimableQueueManager` sub-interface because both adapters implement it (the in-memory one as a no-op), the dispatcher already depends on `QueueManager`, and every call site that would need `ReclaimableQueueManager` is exactly the set that already needs `QueueManager`. A new interface would be premature abstraction.

- **AD-3: The reclaim is Lua-script atomic, no `WATCH`/`MULTI`.** Per clarifications Q2=A. Matches the codebase's established pattern (`CLAIM_SCRIPT`, `ENQUEUE_IF_ABSENT_SCRIPT`, `RELEASE_SCRIPT`), single round trip per orphan, server-side atomicity guaranteed. The iteration-side `EXISTS` check (outside the script, per FR-001) plus the script-internal `EXISTS` re-check (per FR-004) together satisfy US2 race safety — the outer check is an optimization that avoids invoking the script for the >99% healthy-worker case; the inner check is the actual load-bearing guard.

- **AD-4: Sequential invocation in `reaperLoop`, not parallel.** `reapStaleWorkers()` then `reapOrphanClaims()`. The in-memory pass may `queue.release()` items it owns — which decrements `IN_FLIGHT`. If the two ran in parallel, the Redis pass could observe the mid-mutation state. Sequential means the Redis pass always sees a coherent state and the extra cost is bounded (each pass is O(N-active-workers), and N is currently 1 per replica).

- **AD-5: Grace window is inside the Lua script, not the outer loop.** Per FR-005. The grace window's purpose is to defend against a hypothetical race where the claim hash exists before the heartbeat SET completes (impossible under `CLAIM_SCRIPT`'s current atomicity, but robust against future refactors). Embedding it in Lua keeps the guarantee co-atomic with the mutation — an outer-loop check could be stale by the time the script runs. `now` is passed in as an `ARGV` argument because Lua on Redis doesn't expose wall-clock time.

- **AD-6: `attemptCount++` on reclaim; never dead-letter from the reaper.** Per clarifications Q3=C. The observed incident was a cluster restart mid-claim — the item was blameless. Option A (increment + dead-letter after `maxRetries` reclaims) would steadily condemn healthy work every time the cluster restarts. Option B (preserve) hides pathological items (OOM on a giant diff). Option C keeps the counter diagnostic while limiting dead-letter authority to the `release()` path where the item's own execution actually failed. The FR-008 log line includes both pre- and post-increment counts so an operator can tell the two paths apart in log queries.

- **AD-7: Shared helper is pure and stateless; state Map lives at the caller.** `classifyDropSeverity` takes the state as a parameter and returns the mutated state, rather than owning a Map internally. This mirrors `pr-feedback-monitor-service.ts`'s existing `lastUnresolvedThreadCount` pattern (state lives on the service instance) and keeps the helper testable without ceremony. Each caller owns exactly one Map — one on the Redis adapter, one on the in-memory adapter, one per monitor service — so state is instance-scoped and doesn't leak across tests.

- **AD-8: The four monitor drop sites keep their current shape — two log lines per drop (adapter-level + context-level).** Per FR-007. The adapter emits the generic `{ itemKey, reason: 'in-flight', ageMs }` line; the monitor emits the context-rich `{ itemKey, reason: 'in-flight', prNumber, ... }` line. Both share the *same* transition-edge decision because both dispatch through the *same* helper — but they maintain *separate* state Maps (the adapter's Map is independent from each monitor's Map). This is intentional: an adapter-level Map keyed on `itemKey` is authoritative across all four drop sites, and each monitor's Map is authoritative for that surface's context line. Divergence would only appear if the two ageMs sources disagreed, which they don't (both read from the same claim hash's `enqueuedAt`). SC-004 asserts they don't diverge.

- **AD-9: The reclaim's re-enqueue uses `queueReason: 'resume'` and priority 0.** Matches `handleLeaseExpired`'s existing behaviour (`worker-dispatcher.ts:267-273`). A resurrected item should get resume priority so it lands ahead of new work — an operator's mental model of "the worker crashed; the item comes back at the front of the queue" is preserved.

- **AD-10: No `error` tier, no second threshold.** Per clarifications Q4=A. A second tier at `2 × T` would add ~12 additional `error` lines for one stuck item — alarm volume, not signal. If reclaim works, prolonged staleness should not occur; a second severity tier optimises for the case this fix eliminates.

- **AD-11: Monitor-side needs `hasInFlightAge` — a new observability accessor.** Contract §3. The adapter's transition-edge dispatch inside `enqueueIfAbsent` already has the claim payload in hand (from `HGETALL` on the outer loop, cached across the script call). The monitor sites do NOT — they only have the itemKey. To compute `ageMs` on the monitor side without duplicating the `HGET` in every site, a new `QueueManager.hasInFlightAge(itemKey): Promise<number | null>` accessor returns the age (returning `null` on transport error or if the itemKey is no longer in flight, in which case the monitor doesn't emit a drop line at all — it just re-enqueues on the next poll). The adapter's implementation: iterate `SCAN CLAIMED_KEY_PREFIX*` looking for the itemKey. This is O(N-workers) worst case, but the drop path is not hot (it fires only on collision) and N is small. Cheaper than adding a secondary index.

- **AD-12: The in-memory adapter's `reapOrphanClaims` is a no-op returning an empty `ReapReport`, not omitted.** Per FR-011 / Q5=C. This keeps the `QueueManager` interface uniform (both adapters implement every method) and lets the dispatcher call `queue.reapOrphanClaims()` unconditionally without a Redis-vs-in-memory branch. The tests written against the in-memory adapter still exercise the `enqueueIfAbsent` severity dispatch via the shared helper (log-escalation parity, per Q5=C).

## Risks & Mitigations

- **R1: The Lua script's server-side `EXISTS` re-check races with a worker that re-appears mid-script.** Impossible under Lua's atomic-execution guarantee — Redis executes the entire script body without interleaving any other command. The re-check happens as the first statement of the script; if the heartbeat is set even one microsecond before the script starts, the check returns `1` and the script aborts. Mitigation: SC-002 tests this at 100 concurrent live workers.

- **R2: A dispatcher replica loses network connectivity to Redis mid-sweep, and another replica double-reclaims the same orphan.** The Lua script's `EXISTS` re-check plus `HDEL` on the claimed key means the first script to complete wins — the second finds an empty hash and its `HGET`/`HDEL` no-ops. The re-enqueue is guarded by `SREM in-flight` + `ZADD pending` inside the same script body; a second script run for the same `(workerId, itemKey)` finds nothing to reclaim and returns the "heartbeat re-appeared" code (because the first script's `SREM` already dropped the itemKey from in-flight — actually no, `SREM` on in-flight doesn't prevent the second reclaim; the guard is that the second script's `HGET claimedKey itemKey` returns nil, so it has nothing to write into pending). Mitigation: additional guard — the script `HGET`s the payload first; if nil, return an abort code (skipped: nothing to reclaim). This handles the double-dispatcher case cleanly.

- **R3: The `SCAN` cursor iterates a very large keyset and blocks the dispatcher.** `SCAN` is non-blocking on the Redis server side (it advances a cursor rather than walking the whole keyspace atomically). The keyset is O(N-active-workers) = 1-10 keys in practice (`worker-dispatcher.ts:302-306` docs one worker per replica). `SCAN COUNT 100` finishes in a single iteration for realistic sizes. If a future refactor increases N, the sweep still runs in bounded steps — the dispatcher just does fewer of them per cadence.

- **R4: A newly-cleaned claim hash (empty after `HDEL`) is left behind by `HDEL` instead of being `DEL`ed.** The Lua script does `HDEL claimedKey itemKey`, then `HLEN claimedKey`; if zero, `DEL claimedKey`. Redis's empty-hash-is-not-a-hash quirk (empty hashes are automatically deleted by Redis when their last field is removed) actually makes the explicit `DEL` redundant, but including it makes the behaviour identical across Redis 6/7 and cheap. Mitigation: covered by SC-007 (no change to hot-path op counts) via `MONITOR` inspection during a normal claim/complete cycle.

- **R5: The `hasInFlightAge` accessor for the monitor sites does an O(N-workers) `SCAN` per drop, and drops fire on every monitor cycle.** At healthy-cluster N=1-10 workers, this is 1-10 `SCAN` steps + `HGET` per drop, ~2ms overhead. Drops fire at most once per monitor cycle per issue (~5 min interval per PR-feedback poll), so total added Redis load is negligible. If future scale changes this (many workers, many wedged items), the fix is a secondary index `orchestrator:queue:in-flight-items-enqueuedAt` (a `ZSET` of `itemKey → enqueuedAt-ms`). Deferred until measured.

- **R6: The transition-edge tracking Map grows unbounded if wedged itemKeys pile up.** Each entry is O(64 bytes) worst case (itemKey + severity + wrapper). Wedged items are rare; even 10,000 wedged over a year is ~640 KB. Mitigation: cleanup on `complete()` — when the adapter's `complete()` runs, `delete(itemKey)` from the transition-edge Map. Not on the hot path; single Map deletion, O(1).

- **R7: The regression test's mock diverges from real Redis behaviour, and a Lua-script correctness bug slips through.** The mock in `redis-queue-adapter.enqueueIfAbsent.test.ts:16-125` models the script's *contract* (SISMEMBER + SADD + ZADD atomicity) rather than executing the Lua body. Mitigation: (a) the new orphan-reclaim test asserts the *observable behaviour* (claim gone, in-flight cleared, pending has resume item, subsequent enqueueIfAbsent succeeds) rather than the exact command sequence; (b) the changeset carries the note that a real-Redis integration test is a follow-up if the FR-009 mock fidelity proves insufficient in practice (deferred as spec Out of Scope §manual intervention).

- **R8: A future refactor splits the `CLAIM_SCRIPT`'s atomicity (claim hash SET before heartbeat SET), and the grace window is smaller than the split window.** The default grace window is `2 × heartbeatCheckIntervalMs` (30s at defaults). A split large enough to exceed 30s would be a much bigger design change than this fix contemplates. Mitigation: FR-005's grace window is the defensive check; if a refactor needs a larger window, the same schema knob (or a `graceWindowMs` sibling knob) can be raised. Not a code change in this fix.
