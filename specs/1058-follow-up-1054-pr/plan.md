# Implementation Plan: Periodic in-flight/claim reconciliation to close #1054 finding 6 residue

**Feature**: `RedisQueueAdapter.reconcileInFlight()` — periodic sweep that computes `orphaned = in-flight-items \ (pending ∪ claimed)` client-side, gates every candidate `SREM` on a two-sweep confirmation (in-memory tracker Map), and folds each confirmed removal into an atomic `SISMEMBER`+`SREM` Lua invocation. Composed with existing `reapOrphanClaims` inside `worker-dispatcher.ts::reaperLoop` on the same cadence, plus one boot-sweep at process start.
**Branch**: `1058-follow-up-1054-pr`
**Status**: Complete

## Summary

`RedisQueueAdapter.reapOrphanClaims()` (`packages/orchestrator/src/services/redis-queue-adapter.ts:573`) is candidate-set-driven by `orchestrator:queue:claimed:*` keys — it iterates worker claim hashes and reclaims entries whose worker heartbeat is absent. That closes the incident-reported wedge shape from #1054 (heartbeat-ABSENT candidates in a live claim hash). The reviewer of PR #1056 (finding 6) explicitly called out the residual gap: an `itemKey` that exists in `orchestrator:queue:in-flight-items` **without** a matching claim-hash entry is unreachable from the claim-side sweep. Sources: Redis memory-pressure eviction of a claim hash, a future refactor that `HDEL`s without a paired `SREM IN_FLIGHT_KEY`, or out-of-band operator action (the 2026-07-28 15:18Z tetrad-development incident). Every subsequent `enqueueIfAbsent()` for that issue is silently dropped by `ENQUEUE_IF_ABSENT_SCRIPT`'s `SISMEMBER` guard; no code path un-wedges it. The current code already advertises this gap in a `#1054 finding 6 — KNOWN RESIDUE` docstring at `redis-queue-adapter.ts:566-571` that names this issue as the tracker.

The fix per the spec + clarifications:

1. **FR-001 / clarifications Q1=D — Snapshot detection + two-sweep confirmation gate.** New `RedisQueueAdapter.reconcileInFlight(now?: number): Promise<ReconcileReport>`. Detection is client-side and cheap: `SSCAN IN_FLIGHT_KEY` (bounded `COUNT`) for candidates, `ZRANGE PENDING_KEY 0 -1` (parse `itemKey` per member) for pending, `SCAN orchestrator:queue:claimed:*` + `HKEYS` per claim hash for claimed, set-difference in memory → `residueCandidates`. Action is gated: each candidate must be observed as residue in **two consecutive sweeps** before removal. Cross-sweep state lives in an in-memory `Map<itemKey, firstSeenSweepId>` on the adapter (same shape as existing `dropLogState` / `enqueuedAtCache` — instance-scoped, bounded by residue population). First-sweep observation logs at `debug` (`event: 'orphan-in-flight-tracked'`); second-sweep confirmation invokes a new Lua `RECONCILE_IN_FLIGHT_SCRIPT` that atomically `SISMEMBER`+`SREM`s (returns `skipped-race-reappeared` if the item re-entered the SET between the client-side residue computation and the Lua invocation). Candidates not present in the current sweep's residue set are dropped from the Map (transient race artifacts self-clear within one cycle). See Contracts §1 for the script wire shape.

2. **FR-003 / clarifications Q2=B — Co-located cadence + immediate boot sweep.** Reconciliation runs inside `worker-dispatcher.ts::reaperLoop` immediately after `reapOrphanClaims` on every iteration (`heartbeatCheckIntervalMs`, default 30 s per config schema; sibling wired at `worker-dispatcher.ts:588-593` under the same `.catch(...)` error envelope). Additionally, `WorkerDispatcher` fires one reconciliation cycle at startup **before** `reaperLoop`'s first `sleep` at `worker-dispatcher.ts:571`. The boot sweep *arms* pre-crash residue into the tracker Map at t=0 so the first regular sweep at `t=heartbeatCheckIntervalMs` can confirm and `SREM` it — repair begins one cycle sooner than the sleep-first loop would otherwise permit.

3. **FR-004 / clarifications Q3=C / Q4=B — Structured logging with cache cleanup and per-cycle cap.** Each successful `SREM` emits a `warn` line matching the `orphan-claim-reclaimed` shape: `{ event: 'orphan-in-flight-reconciled', itemKey, ageMs, reason: 'in-flight-no-pending-no-claim' }`. `ageMs` is read from `enqueuedAtCache` (`redis-queue-adapter.ts:490-500`); a cache miss emits `ageMs: null` (mirrors `reapOrphanClaims`'s handling of missing `claimedAt`). On successful `SREM`, both `enqueuedAtCache.delete(itemKey)` **and** `dropLogState.delete(itemKey)` fire — matches the full cleanup semantics of `complete()`, dead-letter, and successful reclaim. Per-cycle log cap: up to `RECONCILE_LOG_CAP = 100` individual warns; beyond the cap, suppress and emit exactly one aggregate `{ event: 'orphan-in-flight-reconciled-batch', count, sampledItemKeys: [<first 10>] }` warn. Cycle summary line at the same site as `reap-orphan-claims` in `worker-dispatcher.ts:600-609`: `{ event: 'reconcile-in-flight', scanned, reconciled, skippedRaceReappeared, trackedFirstSeen }` gated on `reconciled > 0 || skippedRaceReappeared > 0 || trackedFirstSeen > 0` so a fully healthy cycle produces zero log noise.

4. **FR-005 — Interface parity.** `QueueManager.reconcileInFlight` added at `packages/orchestrator/src/types/monitor.ts:320` alongside `reapOrphanClaims`. `ReconcileReport` new exported type: `{ scanned: number; reconciled: number; skippedRaceReappeared: number; trackedFirstSeen: number }`. `InMemoryQueueAdapter.reconcileInFlight()` implementation is a no-op returning `{ scanned: this.inFlightSet.size, reconciled: 0, skippedRaceReappeared: 0, trackedFirstSeen: 0 }` — the in-memory adapter's `pending`/`claimed`/`inFlightSet` are first-class fields that cannot diverge; no reconciliation is required.

5. **FR-006 — Zero touch on existing scripts.** No change to `ENQUEUE_IF_ABSENT_SCRIPT`, `CLAIM_SCRIPT`, `RELEASE_SCRIPT`, `RECLAIM_ORPHAN_SCRIPT`, `REQUEUE_FOR_RESUME_SCRIPT`, or any existing public method. The fix is additive: one new method, one new Lua script, one in-memory tracker Map, one new interface entry, one wiring line in `reaperLoop`, one boot-sweep invocation, one docstring update on `reapOrphanClaims`.

6. **FR-007 — Docstring hygiene.** Update the `#1054 finding 6 — KNOWN RESIDUE` docstring at `redis-queue-adapter.ts:566-571` on `reapOrphanClaims` to reflect that the residue is now closed by `reconcileInFlight`, and cross-reference the new method. Preserve historical context.

7. **FR-008 — Regression coverage.** New `packages/orchestrator/src/services/__tests__/redis-queue-adapter.reconcile-in-flight.integration.test.ts` (real Redis; pattern from `redis-queue-adapter.reclaim-lua.test.ts`) covers wedge-state repair (two-sweep gated), healthy-state no-op, two-sweep TOCTOU safety (transient snapshot false-positive drops from tracker without `SREM`), atomic Lua re-check TOCTOU safety, cache/dropLogState cleanup, log-shape assertion, log-cap enforcement, and boot-sweep behavior. Cross-adapter parity added to the existing `queue-adapter-parity.test.ts`.

## Architectural Decisions

- **AD-1: Detection is client-side snapshot; action is two-sweep-gated.** Per clarifications Q1=D. Detection reads pending + claimed at two different instants and is therefore incoherent — legitimate dispatch transitions (`pending → claimed`) and legitimate release-retry transitions (`claimed → pending`) both temporarily make a live item invisible to a naïve snapshot. A single-snapshot `SREM` can therefore corrupt live state (removing an in-flight member for a live item → next `enqueueIfAbsent` passes its `SISMEMBER` guard → two pending members → two workers on one issue → the exact failure mode #1054/#1060/#1069 exist to prevent). A per-item Lua re-check against a scratch snapshot only atomically re-confirms the stale reading — atomicity against the wrong data is not a guard. The fix: require an itemKey to be observed as residue in **two consecutive sweeps** before removing it. A genuinely wedged item will still be there 30 seconds later; a transient artifact resolves within one cycle. Costs one cycle of latency on a repair path where nobody is waiting.

- **AD-2: The two-sweep tracker lives in process-local memory, not Redis.** Per clarifications Q1=D + Q5. A `Map<itemKey, firstSeenSweepId>` on the adapter instance is sufficient — the tracker is per-dispatcher, and if a dispatcher process crashes mid-tracking, the fresh process's boot sweep re-arms whatever candidates remain and the natural cycle progression resumes. Redis scratch keys would introduce new hash-slot constraints under Redis Cluster (see Q5) and buy nothing — the tracker's purpose is cross-time confirmation on a single dispatcher, not cross-replica coordination. If a future refactor ever needs cross-replica tracking, the scratch key MUST hash-tag with `{queue}` to guarantee same-slot placement with `IN_FLIGHT_KEY`/`PENDING_KEY`.

- **AD-3: The Lua script is minimal — `SISMEMBER` + `SREM` only, `numberOfKeys: 1`.** Per FR-002. The two-sweep tracker (AD-1) closes the class of races the snapshot has by construction; the Lua's role is narrow — catch the single race window where an item genuinely re-entered flight between the client-side residue computation and the specific candidate's Lua invocation. That is one `SISMEMBER` + `SREM` sequence on one key (`IN_FLIGHT_KEY`), so `numberOfKeys: 1`. No `cjson.decode`, no scratch-key comparison, no `HGET` on claim hashes. Zero risk of `CROSSSLOT` errors under Redis Cluster: only one key touched.

- **AD-4: Boot sweep is invoked from `WorkerDispatcher` before the reaperLoop's first `sleep`, not from the adapter constructor.** Per clarifications Q2=B. Boot sweep needs to fire **once** on the actual process, not on every adapter construction (tests construct many adapters). Placing it in `WorkerDispatcher.start()` (the caller that owns `reaperLoop` lifecycle) is the cleanest seam. Exact shape: before `reaperLoop(ac.signal)` is spawned at `worker-dispatcher.ts:111`, fire `this.queue.reconcileInFlight().catch((err) => this.logger.warn({ err }, 'boot reconcileInFlight failed'))`. Fire-and-forget so `start()` returns immediately; the loop's first regular sweep will run its own tracker check regardless. If the boot sweep completes before the first regular sweep (likely under any healthy Redis), pre-existing residue is armed by t=0 and repaired by t=30s. If the boot sweep is slower than the first `sleep` (implausible), the loop still self-heals on subsequent cycles.

- **AD-5: Sequential invocation in `reaperLoop`: `reapOrphanClaims` then `reconcileInFlight`, not parallel.** Same rationale as #1054's AD-4. `reapOrphanClaims` mutates the claim-hash side (reclaims heartbeat-absent claims to pending); running reconciliation immediately after ensures the reconciliation's client-side snapshot sees a coherent post-reap state. Parallel execution could have the reconciliation snapshot `pending` before the reap wrote to it and observe an itemKey as residue that the reap will move to pending microseconds later. The two-sweep gate (AD-1) closes that race even under parallel execution, but sequential execution collapses the window entirely and matches the sibling wiring pattern.

- **AD-6: Cache cleanup on successful `SREM` mirrors `complete()` / dead-letter / successful reclaim.** Per clarifications Q3=C. When an itemKey leaves flight for any reason, both `enqueuedAtCache.delete(itemKey)` and `dropLogState.delete(itemKey)` fire together. This preserves the invariant `hasInFlightAge(itemKey)` returns `null` for itemKeys not in flight — a stale cache entry for a reconciled itemKey would return a fabricated age on the next drop-log call, corrupting diagnostic output. The stated cost (losing `ageMs` if the same itemKey recurs as residue) is negligible — recurrence means a live bug that warrants investigation on its own terms, not a slightly richer log line.

- **AD-7: Per-cycle log cap with aggregate line, not per-itemKey transition-edge throttling.** Per clarifications Q4=B. Q4=C (reuse `classifyDropSeverity`) is a category error: `classifyDropSeverity` throttles per itemKey across repeated observations, but a reconciled itemKey is `SREM`'d exactly once and then ceases to exist — there is no second observation to throttle, so throttling would suppress nothing and add a Map that only grows. Q4=A (unbounded) at 10,000 residue items would drown log ingestion pipelines and bury every other warning in the window, including whichever warning explains the regression that produced the residue. The cap (100 individual warns + one aggregate `orphan-in-flight-reconciled-batch` warn with `{ count, sampledItemKeys: [<first 10>] }`) bounds volume, preserves a diagnostic sample, and makes the aggregate count (the metric that actually indicates scale) a single greppable event.

- **AD-8: Interface widening on `QueueManager`, not a new sub-interface.** Same rationale as #1054's AD-2. Both adapters implement `reconcileInFlight` (the in-memory one as a no-op per AD-9); the dispatcher already depends on `QueueManager`; every future call site would already need `QueueManager`. A `ReconcileableQueueManager` sub-interface would be premature abstraction.

- **AD-9: `InMemoryQueueAdapter.reconcileInFlight` returns `{ scanned: this.inFlightSet.size, reconciled: 0, ... }`, not throws or omits.** Per FR-005. In-memory `pending`, `claimed`, and `inFlightSet` are first-class fields in the same process — they cannot diverge without a bug in the in-memory adapter itself, and in-memory adapter bugs are caught by the existing in-memory-adapter tests (`in-memory-queue-adapter.enqueue-invariant.test.ts` etc.). Returning `scanned: this.inFlightSet.size` (rather than 0) gives the parity test a truthful "sweep did examine the set" signal, and callers that log `scanned` see a real number.

- **AD-10: `RECONCILE_IN_FLIGHT_SCRIPT` returns integer 1 (reconciled) / 0 (skipped-race-reappeared).** Simplest possible wire shape given the single-key single-op semantics. No `attemptCount` to propagate; no `SREM` result to interpret ambiguously (the `SISMEMBER` decides). Follows the return-code convention of `ENQUEUE_IF_ABSENT_SCRIPT` (`0` = dropped/no-op, `1` = mutated).

- **AD-11: Tracker Map is bounded by the natural rate of residue events, not by any explicit cap.** Under healthy operation the map is empty. Under a bug producing steady residue, entries insert on sweep N and delete on sweep N+1 (successful `SREM`) or on the sweep where the candidate re-appears in pending/claimed (dropped from map without SREM). A candidate that stays in residue indefinitely is `SREM`'d on the second sweep and removed from the tracker. So the tracker size is bounded by the residue population between two consecutive sweeps — a bounded quantity regardless of long-term residue count. No explicit cap or eviction policy needed.

- **AD-12: The `SSCAN` cursor semantics tolerate mutation mid-sweep.** New members added to `IN_FLIGHT_KEY` between two `SSCAN` calls of the same cursor iteration may or may not be returned by this sweep (per Redis docs); those missed will be found on the next cycle. Since we're only looking for residue (members that persist across cycles anyway), this is a non-issue — a transient new member added mid-sweep can't be residue in the current cycle by definition.

- **AD-13: No `heartbeatCheckIntervalMs`-independent knob.** Per clarifications Q2=B. The reconciliation shares the reaperLoop's cadence directly. If a future need for independent tuning emerges (e.g., a very-large-cluster deployment wants a slower reconciliation cadence than heartbeat-check), a `reconciliationIntervalMs` field can be added to `DispatchConfigSchema` at that time. Adding a knob now with no evidence of need would be YAGNI.

## Risks & Mitigations

- **R1: The two-sweep gate misses a wedge that self-resolves via `enqueueIfAbsent` in the intervening cycle.** Under the current design, the primary intake paths (`enqueueIfAbsent` / `enqueue`) cannot re-populate a wedged itemKey — `SISMEMBER` returns 1 and the enqueue is dropped. So there is no path by which a wedged itemKey legitimately returns to pending between two sweeps. If a future refactor changed this (e.g., added a direct `ZADD PENDING_KEY` bypassing `enqueueIfAbsent`), the two-sweep gate would correctly drop the candidate from the tracker without `SREM`, which is the safe outcome. No mitigation needed; the design is fail-safe under this class of drift.

- **R2: `ZRANGE PENDING_KEY 0 -1` on a very large pending set blocks Redis for the duration.** The pending set size is bounded by the number of unclaimed issues awaiting dispatch — typically 0-10, occasionally spikes to hundreds on a startup or after a broad label sync. A `ZRANGE` over 100 members takes microseconds on Redis. Under a pathological scenario (10,000+ pending), the sweep still completes in bounded time (Redis single-threaded execution is fast for `ZRANGE`; the bottleneck would be network transfer + JSON parsing client-side). Mitigation: if measured latency becomes a concern, switch to a bounded `ZSCAN` loop mirroring the `SSCAN` pattern. Deferred until measured (spec Out of Scope §performance).

- **R3: `SCAN claimed:*` + `HKEYS` per claim hash is O(workers). At scale (100+ workers) the per-cycle cost climbs.** Same argument as R2 above — worker count is 1-10 today, and the loop is already used in production by `reapOrphanClaims` at the same cadence. If future scale changes the picture, add a secondary index (e.g., `ZSET claimed-itemKeys` with score = enqueuedAt). Deferred until measured.

- **R4: The tracker Map grows unbounded under a bug that produces continuous new residue faster than the sweep can `SREM`.** Impossible under normal operation (steady-state residue count is bounded by the underlying failure rate); under a pathological bug the operator sees the per-cycle `reconcile-in-flight` summary line with an ever-growing `reconciled` count and investigates. The Map itself is bounded per-cycle to the current residue population (AD-11), not to historical count.

- **R5: A dispatcher replica loses connectivity mid-sweep and the tracker Map is lost.** Fresh process's boot sweep (AD-4) re-arms whatever residue remains. Cost: one cycle of additional latency for pre-crash tracker state. No permanent effect — residue is a property of Redis state, not client state.

- **R6: The Lua script's `SISMEMBER` returns 1 for an itemKey that was just re-added by a concurrent `enqueueIfAbsent`, and the `SREM` removes a legitimate live item.** This is the race the atomic Lua exists to close. Once the two-sweep gate has confirmed the candidate (i.e., the item has been residue for one full sweep cycle), a concurrent `enqueueIfAbsent` between the tracker confirmation and the Lua invocation is the only remaining window. The Lua atomically re-checks `SISMEMBER`; if `SISMEMBER == 0`, the item is already gone (concurrent `SREM` from another actor — impossible under our code paths, but safe outcome). If `SISMEMBER == 1`, we `SREM` — and if the concurrent `enqueueIfAbsent` fired *after* our `SISMEMBER` but before our `SREM`, the Lua's atomicity means the `SREM` fires on the state where the item was present, and the concurrent enqueue's `SADD` fires after the `SREM` — final state: item in SET, item in pending, worker picks it up. No corruption. Mitigation: SC-003 tests this at 100 concurrent `enqueueIfAbsent` calls racing a confirmed reconciliation.

- **R7: Boot sweep's fire-and-forget fails silently.** The `.catch((err) => this.logger.warn(...))` envelope ensures a Redis transport failure at boot logs a `warn` and returns; the next regular sweep at `t=heartbeatCheckIntervalMs` retries. No hidden failure mode.

- **R8: A regression that stops calling `reconcileInFlight` from `reaperLoop` goes undetected.** The FR-008 wedge-repair regression test asserts that after two reaper cycles, a directly-`SADD`'d wedge is `SREM`'d. If `reaperLoop` stops calling `reconcileInFlight`, this test fails. SC-006 explicitly covers this.

- **R9: A future refactor adds a scratch key inside `reconcileInFlight` without hash-tagging.** Clarifications Q5=B rejected explicitly. Documented in the plan (AD-2), in the docstring on the tracker Map, and in spec Out of Scope. A reviewer catching a new scratch key in a follow-up PR should point at this note.
